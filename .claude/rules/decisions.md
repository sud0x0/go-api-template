# Settled decisions

Deliberate trade-offs already made in this codebase, each with a one-line
rationale and a code citation. **Do not relitigate these unless the user
explicitly asks.** A proposal that contradicts an entry here is a finding to
flag against this file, not a default to adopt. When you add a new deliberate
trade-off, record it here so the next reviewer (human or agent) doesn't re-open it.

| 1 | **Offset AND cursor pagination coexist** on `GET /api/v1/logs`. | Offset is simple for shallow/UI paging, and cursor (keyset) is constant-cost and insert-stable for deep/unbounded walks. Both keep their place. | [`userlog_handler.go` ListLogs](../../internal/userlog/userlog_handler.go), [`userlog_repository.go`](../../internal/userlog/userlog_repository.go) |
| 2 | **Response-shape asymmetry kept** for backwards compatibility: offset-mode returns a **bare array** `[…]`, and cursor-mode returns the wrapped `CursorPage` `{"logs":[…],"next_cursor":"…"}` (`next_cursor` omitted on the last page). | Changing the offset response to an object would break existing clients. The asymmetry is documented in the OpenAPI spec. | [`userlog_model.go` `CursorPage`](../../internal/userlog/userlog_model.go) |
| 3 | **Cursors are opaque but UNSIGNED**: base64url of `(date_and_time, id)`, no HMAC. | Every query stays `user_id`-scoped, so a forged cursor cannot cross user boundaries. It can only reposition within the caller's own rows. Signing would add key management for no security gain. Malformed cursors are rejected (strict RFC3339Nano + UUID) before any SQL. | [`userlog_cursor.go`](../../internal/userlog/userlog_cursor.go) |
| 4 | **Rate limiting is edge-first.** The app limiter is an opt-in fallback (`RATE_LIMIT_RPM`, default `0` = not even registered), keyed by client IP, counters in-memory **per instance**. | The primary control belongs at the LB / gateway / WAF. | 5 | **The internal admin router keeps chi's plain-text defaults** (no JSON envelope on its 404/405). | `:METRICS_PORT` is an operator-only surface with no auth, restricted at the infra layer. | 10 | **The UUID user-ID contract is enforced at the single READ point** (`shared.UserIDFromContext` canonicalises and rejects non-UUIDs as 401). `WithUserID` stays a plain setter. | One enforcement point means a second writer can't bypass validation. | 11 | **`WriteTimeout` MUST be greater than `RequestTimeout`**, validated at startup. | A write window shorter than the handler timeout silently truncates slow responses (surfaces as "connection reset"). | 12 | **Single-statement repository methods are never wrapped in a transaction.** | A lone statement is already atomic. `WithTransaction` would add a round-trip for nothing. Disabled-by-default keeps local dev zero-setup. | 16 | **The app is an OAuth2 RESOURCE SERVER, not an authorization server and not a browser OIDC client.** It receives a Bearer access token in the `Authorization` header, validates it with go-oidc against the IdP's discovered JWKS, and enforces access. The login redirect, code exchange, PKCE, `state`/`nonce`, redirect-URI registration, and refresh rotation are NOT implemented. They belong to the adopter's IdP and frontend (see #19). | A template cannot guess an adopter's login UX, but every adopter's API must validate the token it is handed. Shipping only the resource-server half is the reusable, non-presumptuous slice. go-oidc is the validation library because it wraps discovery + `RemoteKeySet` (JWKS fetch/rotate) and refuses token-supplied `jku`/`x5u`/`jwk`. `oidc.InsecureIssuerURLContext` is deliberately NOT used (exact issuer match, ASVS V10.5.3). `OIDC_AUDIENCE` must be this API's OWN audience identifier (the value the IdP stamps into ACCESS-token `aud`), never a browser client_id: an ID token's `aud` IS the client_id, so equating them would let an ID token pass audience validation (token-type confusion). ID tokens are additionally rejected by `token_use` and the OIDC-Core ID-token-only claims `nonce`/`at_hash`/`c_hash`. | [`internal/middleware/auth_middleware.go`](../../internal/middleware/auth_middleware.go), [`internal/config/config.go` `OIDCConfig`](../../internal/config/config.go) |
| 17 | **Authorisation is an OPA sidecar consulted over its REST Data API, fail-closed, FUNCTION-LEVEL only.** The middleware POSTs `{input:{subject,roles,action,resource,method,target_user}}` to `OPA_URL/OPA_DECISION_PATH` and allows ONLY on an explicit `result==true`. Any error (timeout, non-200, malformed body, missing result) denies with 403. `input.resource` is the chi LEAF route pattern (e.g. `/api/v1/logs/{id}`), which requires the OPA middleware to run AFTER chi resolves the route: it MUST be registered as a POST-ROUTING (inline-group) middleware via `middleware.AuthorizedRoutes`, NOT a pre-routing `r.Use` on the `/api/v1` subrouter. A pre-routing `r.Use` runs before chi matches the leaf and hands OPA the MOUNT pattern `/api/v1/*`, which the policy's `is_logs` never matches, so every request is denied 403 and the whole authz layer is silently non-functional (this was a real bug). The repository's `WHERE user_id = $N` SQL scoping stays as the ROW-OWNERSHIP layer and is NOT moved into OPA. | REST (not gRPC, not the Envoy external-authz variant) because the app calls OPA directly, so the standard `openpolicyagent/opa` image suffices with no Envoy in the path and a lighter dependency tree. Fail-closed is the security-critical default: an OPA outage becomes a visible 403, never an authorisation bypass. Keeping row ownership in SQL is defence in depth. OPA answers "may this role call this endpoint", the SQL answers "may this user see this row". Collapsing them would put row filtering behind a network hop and a policy edit. The post-routing wiring is a chi mechanic (inline-group middleware is baked into the endpoint handler, so it runs after `FindRoute` sets the pattern) captured once in `AuthorizedRoutes` so no feature can re-introduce the mount-pattern bug. | [`internal/middleware/authz_middleware.go`](../../internal/middleware/authz_middleware.go), [`internal/middleware/routing.go`](../../internal/middleware/routing.go), [`cmd/api/main.go`](../../cmd/api/main.go), [`deploy/opa/policy.rego`](../../deploy/opa/policy.rego), [`compose.dev.yaml`](../../compose.dev.yaml) |
| 18 | **External identity maps to the internal UUID via `UUIDv5(fixed-namespace, iss\|sub)`, computed in the auth middleware, no lookup table.** IdP roles/groups map to internal roles at the same boundary (`mapClaimsToRoles`), so the policy is written against internal role names. | The `user_id` column is `UUID NOT NULL` but an IdP `sub` is often not a UUID (`auth0\|12345`, an email). A deterministic v5 derivation is reproducible across restarts and replicas with zero infrastructure, and including `iss` stops two IdPs colliding on the same `sub`. It is documented as swappable: a real deployment may keep a `users` table mapping `(iss,sub)→id` and resolve it in the middleware before `WithUserID`. `UserIDFromContext` still enforces the UUID shape at the single read point (#10). The role side of the boundary is DENY BY DEFAULT: `mapClaimsToRoles` trusts NO IdP group/role name as an internal role (an empty allowlist the adopter curates via `mapClaimsToRolesWith`). The starter policy grants global cross-user access on the literal role `admin`, so a verbatim passthrough of the token's roles ∪ groups would hand that privilege to any token merely carrying a group named `admin`; the empty default withholds all elevated/cross-user access until the adopter maps specific trusted names (self-access stays role-independent). | [`internal/middleware/auth_middleware.go` `MapSubjectToUUID`](../../internal/middleware/auth_middleware.go) |

Token storage is the client's concern. The template only documents that browser forks must not use `localStorage`. | These are properties of the login flow, which a resource server never runs. Implementing them would mean guessing the adopter's IdP and UX. The ASVS map records each as `n/a` with the reason "authorization server / OIDC client responsibility" rather than as a gap. | [`internal/middleware/auth_middleware.go`](../../internal/middleware/auth_middleware.go), [`.claude/skills/security-review/references/asvs-map.md`](../skills/security-review/references/asvs-map.md) |
| 20 | **A Backend-For-Frontend (BFF), if an adopter uses one, is a SEPARATE component that sits in front of this API and is never this API itself.** Under the BFF pattern the BFF is a distinct service that holds the user's tokens (typically in a same-site `HttpOnly` cookie or a server-side session) and calls this API with a Bearer token on the user's behalf. This API is only ever the resource server on the receiving end. A companion frontend or UI template must treat this API as a resource server it calls, not as its own token holder. | A resource server validates a token it is handed (#16) and runs no login flow and holds no client tokens (#19), so it structurally cannot also be the token-holding BFF for its own callers. Writing this down stops a cross-repo mix-up where a frontend assumes this service stores its tokens. | [`internal/middleware/auth_middleware.go`](../../internal/middleware/auth_middleware.go), [`README.md`](../../README.md) auth note |
| 21 | **Authorisation is ATTRIBUTE-BASED (ABAC), evaluated by OPA, with Level 2 cross-user read/write/delete gated per object by the policy.** The OPA input carries the caller's attributes (`subject`, `roles`) plus a `target_user` (the owner the request acts on). Self-access is the default (`target_user` == subject); a caller names another owner via the `?user=<uuid>` query parameter. The four fixed action verbs (`read`/`create`/`update`/`delete` from `methodToAction`, unchanged) are the only actions the policy reasons about. The target user MAY come from request input, but the caller's RIGHT to act on it is decided by OPA against TOKEN / trusted-store attributes, never asserted by the request (OWASP API1:2023 BOLA). `target_user` is `uuid.Parse`-validated (400 `invalid_target`, never a 500) before the OPA input is built and before any query. Cross-user runs a SEPARATE target-aware repository path (`*ForTarget`) still scoped to the target's `user_id`; there is NO unscoped whole-table query, so object-ownership enforcement stays at the data layer. The handler goes cross-user ONLY after reading a target the OPA middleware wrote to the context AFTER an explicit allow (fail-closed: OPA disabled → self-access only). CREATE is caller-owned and has no cross-user path. The starter policy ships BOTH a role-only (RBAC-style) rule (`admin` on any target) and a scoped attribute rule (`team-lead` within a `team` boundary fed from a trusted `user_team` table, never request input), demonstrating that RBAC is a special case of ABAC (NIST SP 800-162). One credential system: user tokens and machine Client-Credentials tokens are validated the same way and authorised by the same policy; no bespoke API-key store (a second validation + revocation path OWASP advises against). Auditability tradeoff: ABAC has no static "who can access X" answer, mitigated (not eliminated) by `opa test`, `opa test --coverage`, and OPA decision logs. | The template ships a working attribute-based model an adopter can grow into (role-only stays RBAC), while keeping object-ownership in SQL as defence in depth. Deriving the target from request input but authorising it via OPA is the only way to offer cross-user access without a BOLA hole; validating the UUID at the middleware keeps a malformed target a clean 400. See #10 (single UUID read point), #13 / #16–#19 (two-layer model), and security.md rules 4–5. | [`internal/middleware/authz_middleware.go`](../../internal/middleware/authz_middleware.go), [`internal/shared/identity.go`](../../internal/shared/identity.go), [`internal/userlog/userlog_handler.go`](../../internal/userlog/userlog_handler.go), [`internal/userlog/userlog_repository.go`](../../internal/userlog/userlog_repository.go), [`deploy/opa/policy.rego`](../../deploy/opa/policy.rego), [`deploy/opa/policy_test.rego`](../../deploy/opa/policy_test.rego) |
